# Design Decisions

Every design choice that affects results, with the reason. Newest at the bottom.

| Date | Decision | Reason |
|---|---|---|
| 2026-10-03 | Compute: Kaggle (2× T4) as the main platform, Google Colab as backup | No lab GPU available |
| 2026-10-03 | Full-precision baseline is FP16, not BF16 | T4 GPUs do not support BF16 |
| 2026-10-03 | Qwen2.5-7B in FP16 runs with tensor parallelism across both T4s (superseded below: Qwen2.5 replaced by Qwen3) | About 15 GB of weights does not fit on one 16 GB T4 with room for the KV cache |
| 2026-10-03 | Core scope: 5 models × 5 precisions × 2 decoding modes; everything else is stretch | Fits the 9-week timeline |
| 2026-10-03 | Second model family: Llama-3.2-1B/3B; Phi-4-mini as fallback if access is denied | Two sizes in a second family; designed for on-device use; xLAM-2-1b and Hammer2.1 are Qwen-based |
| 2026-10-03 | License: MIT | Permissive and standard for research code |
| 2026-10-03 | BFCL pinned to `bfcl-eval==2026.3.23` with vLLM 0.8.5, in a separate Python 3.11 environment | Latest BFCL release; vLLM 0.8.5 is the version BFCL pins for local models and still supports T4 GPUs |
| 2026-10-03 | The vLLM server is started manually in FP16, and BFCL connects to it with `--skip-server-setup` | BFCL always launches vLLM with `--dtype bfloat16`, which a T4 cannot run |
| 2026-10-03 | BFCL reproduction model: `Qwen/Qwen3-4B-Instruct-2507`, prompt and FC modes | BFCL v4 dropped Qwen2.5 (July 2025), so Qwen2.5 has no current leaderboard score to compare with; this model is on the leaderboard in both modes, has no thinking mode, and fits on one T4 |
| 2026-10-03 | Qwen family switched from Qwen2.5 to Qwen3: Qwen3-1.7B, Qwen3-4B, Qwen3-8B (Qwen3-0.6B as stretch) | BFCL v4 dropped Qwen2.5; Qwen3 is the current generation and has BFCL v4 leaderboard scores; the three sizes replace Qwen2.5-1.5B/3B/7B one for one |
| 2026-10-03 | Qwen3 runs with thinking mode off (`enable_thinking=False`) | All three sizes come from the same release; short outputs keep T4 runs fast; comparable with Llama-3.2, which has no thinking mode |
| 2026-10-03 | Qwen3-8B in FP16 runs with tensor parallelism across both T4s | About 16 GB of weights does not fit on one 16 GB T4 |
| 2026-10-03 | GPTQ and AWQ checkpoints are made with one recipe for every model, not downloaded | Qwen publishes official AWQ only for Qwen3-4B/8B and no 4-bit GPTQ at all; one recipe for all models keeps the comparison fair |
| 2026-10-05 | The study's 4B model is `Qwen/Qwen3-4B` (thinking off), not `Qwen/Qwen3-4B-Instruct-2507` | Same release and training as Qwen3-1.7B and Qwen3-8B, so size is the only difference between the three; Instruct-2507 has no 1.7B or 8B version. BFCL has no `Qwen/Qwen3-4B` entry and scores Qwen3-1.7B/8B with thinking on, so the core Qwen models have no comparable leaderboard score; our own FP16 runs are the baseline |
| 2026-10-05 | `Qwen/Qwen3-4B-Instruct-2507` is kept only as the sanity check for our own evaluation script (Update 3), compared with the BFCL run (86.31% prompt, 87.81% FC) | It is the only model with a BFCL run on our hardware. Our script uses its own prompt format, so a few points apart is fine; a big gap means a parsing bug |
| 2026-10-12 | Prompt format of our own script: one system prompt that asks for a JSON array `[{"name": ..., "arguments": {...}}]` (an empty array `[]` means no call), used in both free and constrained mode. The wording follows BFCL's default prompt, and the functions are listed as JSON, as in BFCL | The constraint is then the only difference between the two modes. A JSON array is also what constrained decoding produces |
| 2026-10-12 | Java and JavaScript questions keep BFCL's language hints: every parameter is shown as a string, and BFCL's checker converts it back | This is what BFCL shows the model in both prompt and FC mode, and what its checker expects |
| 2026-10-12 | Decoding: greedy (temperature 0, top-p 1, top-k off), seed 42, at most 4,096 answer tokens, max_model_len 8,192. Every value is set in the config file | No sampling value comes from the model's generation_config (unlike the Update 2 BFCL run; vLLM only takes the model's end-of-text tokens from it), so precision is the only thing that changes between runs. 4,096 is BFCL's answer budget; the longest prompt is about 1,250 tokens |
| 2026-10-12 | Parser: only surrounding whitespace and one Markdown code fence are tolerated. Anything else (extra text, other keys, a single object instead of an array) is a parse failure | Repairing answers would hide exactly the syntactic failures this study measures |
| 2026-10-12 | Scoring: BFCL's own AST checker from bfcl-eval 2026.3.23. An irrelevance answer is correct when it contains no call, as in BFCL; whether it parsed is stored separately | Keeps our scores comparable with BFCL. Checked on the Update 2 FC answers: the same verdict as BFCL on all 1,390 questions (`src/check_scorer.py`) |
| 2026-10-12 | Overall score = BFCL's Non-Live Overall Acc: the unweighted mean of simple (itself the mean of Python, Java and JavaScript), multiple, parallel and parallel-multiple. Irrelevance is reported separately | The same formula as BFCL's `data_non_live.csv` and the leaderboard |
| 2026-10-12 | Every config pins the model to a Hugging Face commit hash | An update to a model during the study cannot change the results |
| 2026-10-12 | Constrained mode: vLLM guided decoding with the xgrammar backend, with no fallback to another backend and no free whitespace. The schema (`src/schema.py`) keeps types, enums, array items, object properties and required fields; extra keys are not allowed. First version; Update 7 revisits it | All 1,390 schemas compile in xgrammar 0.1.18 (the version vLLM 0.8.5 uses). BFCL's checker rejects extra parameters anyway. Free whitespace can make Qwen models generate whitespace without end (vLLM warns about this) |
| 2026-10-12 | Llama-3.2 prompts use a fixed date (`date_string: "26 Jul 2024"`, the template's own default) | Llama's chat template otherwise writes the current date into the system prompt, so runs on different days would get different prompts |
| 2026-10-12 | Qwen3-8B (two T4s) runs with vLLM's custom all-reduce turned off, using plain NCCL | The two T4s are connected over PCIe without NVLink; this skips vLLM's peer-to-peer test and its custom kernel. It changes only how the two GPUs exchange data, not the model |
| 2026-10-29 | INT8 is bitsandbytes LLM.int8 (8-bit weights, threshold 6.0). The checkpoint is made beforehand with transformers (`src/quantize.py`) and vLLM runs it in eager mode | First choice in the plan, and it works on a T4. vLLM's quantize-on-load mode is always 4-bit NF4, it loads 8-bit bitsandbytes models only if they are already quantized, and it has no CUDA graphs for them |
| 2026-10-29 | NF4 uses vLLM's own bitsandbytes mode: quantized while loading, 4-bit NormalFloat, blocks of 64, double quantization | No checkpoint is needed, so the weights come straight from the pinned model |
| 2026-10-29 | Every quantized run uses one T4, including Qwen3-8B. FP16 Qwen3-8B stays on two | At 8 bits (8.80 GiB) and 4 bits (5.67 GiB) it fits on one T4, and vLLM cannot split an already quantized bitsandbytes model. FP16 Qwen3-8B's speed is therefore not compared with the one-GPU runs |
| 2026-10-29 | Qwen3-8B INT8 runs with `gpu_memory_utilization: 0.81`; all other runs use 0.90 | 0.90 ran out of GPU memory: 8-bit bitsandbytes needs more temporary memory than vLLM's profile measures. At 0.81 the KV cache still fits one 8,192-token request (about 9,400 tokens) |
| 2026-10-29 | GPTQ and AWQ recipe, the same for all five models: GPTQModel 5.7.0, 4 bits, group size 128, no plain-rounding fallback. GPTQ is symmetric with `desc_act` off; AWQ has a zero point and uses the GEMM format | vLLM 0.8.5 runs these two formats on a T4. It runs llm-compressor's 4-bit format only on newer GPUs (compute capability 8.0; the T4 is 7.5). GPTQModel 5.7.0 is the last release that supports transformers 4.x |
| 2026-10-29 | One calibration set for GPTQ and AWQ: the first 256 English C4 documents (`en/c4-train.00001-of-01024.json.gz`, revision `1588ec4`) with at least 3,000 characters, cut to 512 tokens | The same documents for every model; only the tokenizer differs. General text, with no BFCL questions in it |
| 2026-10-29 | GPTQModel runs in its own Python environment (torch 2.9.1, transformers 4.57.6), without building its compiled kernels. The saved `config.json` is the base model's plus GPTQModel's `quantization_config` | It needs a newer transformers than vLLM 0.8.5 uses, and vLLM reads `config.json` with the older one. vLLM runs the models, so GPTQModel's own kernels are not needed |
| 2026-10-31 | AWQ's calibration runs 16 documents at a time (`batch_size: 16` in the AWQ configs). All 256 are still used | With the default, GPTQModel runs all 256 in one pass in AWQ's scale search, which ran out of memory on a T4. GPTQ keeps batch size 1 |
| 2026-11-01 | `src/quantize.py` skips GPTQModel's check for its compiled AWQ kernels | Saving AWQ weights fails that check, but only running a model in GPTQModel uses those kernels, and here vLLM runs the model. Tested with real GPTQModel on small random models; all five full AWQ checkpoints used it |
| 2026-11-02 | Qwen3-8B AWQ loads its weights from an FP16 copy on disk (`fp16_copy: true` in its config). The other checkpoints do not | The Qwen3-8B AWQ job stopped in its first layer with no error, most likely out of system memory: GPTQModel converts the BF16 weights to FP16 in RAM (about 15 GiB), and AWQ keeps the layer's activations in RAM too. Weights already in FP16 stay on disk until needed. On small test models the saved checkpoint is bit-identical with and without the copy |
| 2026-11-02 | Qwen3-8B AWQ limits AWQ's channel scales: a channel's mean activation counts as at least 0.001 × the median, and every scale stays between 1/100 and 100 (`x_mean_floor: 0.001`, `max_scale: 100` in its config). The other checkpoints do not | In layer 2, some channels had a mean activation of 0, and AWQ gave them scales up to 2,450. `up_proj`'s outputs then passed FP16's largest value (65,504), the next layer got only NaN, and the job stopped. AWQ scores this group at `down_proj`'s output only, so its search did not catch the overflow. Found with two read-only probe runs on Kaggle. The two values are a judgment, not tuned. On small test models the limits change no weights when the scales are normal |
| 2026-11-03 | Qwen3-8B AWQ adds up its large tensors in chunks of 128 MiB (`chunk_mib: 128` in its config) instead of GPTQModel's 1 GiB | With 1 GiB chunks it ran out of GPU memory at layer 22 of 36: it needed 1 GiB and 808 MiB was free. The chunk size changes only memory use; on small test models the checkpoint is bit-identical |
| 2026-11-03 | Qwen3-8B AWQ is the one exception to "one recipe": only it uses the FP16 copy, the scale limits and the smaller chunks. Its quantization settings (4 bits, groups of 128, zero point, GEMM format) and calibration documents are the same as for the others | Without these changes the checkpoint could not be made on a T4, and leaving it out would leave a gap in the main table. The settings are in its config and in `results/meta/qwen3-8b_awq_free.json` |
| 2026-11-03 | Failure classes: a failed answer is syntactic if it is not valid JSON (S1) or does not match the schema in `src/schema.py` (S2). Otherwise it is semantic, and BFCL's error type gives the class (M1-M5). The checks run in this order | The schema is the one constrained decoding enforces, so the syntactic classes are exactly the failures it can block (compared in Update 10). An answer with both a format error and a content error counts once, as syntactic |
| 2026-11-03 | The schema allows no extra arguments (`additionalProperties: false`) and only the listed function names. So an invented argument or function name is S2 (syntactic), not M1 or M2 | BFCL's checker rejects both as well, and constrained decoding cannot write either. Allowing them would make "syntactic" differ from "what constrained decoding blocks". In the 25 free runs, 258 failed answers name a function that is not in the list |
| 2026-11-03 | An irrelevance answer that does not parse counts as correct, not as a failure | It makes no call, so BFCL's checker counts it as correct (576 answers in the 25 free runs) |
| 2026-11-03 | `src/taxonomy.py` uses the `jsonschema` package; `src/figures.py` uses matplotlib (3.11.2, on a PC). Neither is added to the run environments | `jsonschema` is already in the vLLM environment (4.26.0 in every freeze file since Update 3). The figures are drawn from the result tables, so the GPU runs do not need matplotlib |
| 2026-11-03 | Each quantized run is tested against FP16 of the same model with McNemar's exact test on the 1,150 AST questions, with Holm's correction over the 20 tests; the size of each change gets a bootstrap 95% interval (10,000 resamples inside each category, seed 42) | Both runs answer the same questions, so a paired test is the right one, and McNemar's uses only the questions where the two runs disagree. Holm keeps the chance of even one false "significant" at or below 5% over all 20 tests. Irrelevance is left out because Overall leaves it out |
| 2026-11-03 | `src/significance.py` computes McNemar's exact p value itself (`math.comb`) instead of calling scipy | One package less (numpy only). Checked against scipy 1.14.1's `binomtest` on all 20 tests: the same p values (largest relative difference 4e-14) |
| 2026-11-03 | The change in `results/significance_free.csv` is the difference of the two Overall values rounded to 2 decimals, as in `results/summary.csv`; the intervals use the unrounded values | So the change matches `results/main_table.md` exactly. Without rounding first, 6 of the 20 changes differed from that table by 0.01 |
| 2026-11-03 | Paper template: IEEE conference (`IEEEtran`), until the supervisor names a venue | A common two-column template; the outline in `paper/main.tex` is in bullet points, so moving it to another template is easy |
| 2026-11-03 | Update 9 made the INT8 and GPTQ checkpoints again, with the same code, settings and main packages (only Python went from 3.11.17 to 3.11.18). AWQ was downloaded from the private Hugging Face repositories of Update 6 | The checkpoints of Updates 5 and 6 were not kept. The new GPTQ checkpoints give the same GPTQ loss as Update 6 on all 1,008 quantized layers, and every INT8 and GPTQ checkpoint loads with the same weight size, so they are taken as the same. The GPTQ checkpoints are now on Hugging Face too |
| 2026-11-03 | The constrained runs were split into part A (Qwen3-1.7B, Llama-3.2-1B, Llama-3.2-3B; commit `d7abb52`) and part B (Qwen3-4B, Qwen3-8B; commit `0cdf81b`), one Kaggle session each | A failure in one session cannot lose all 25 runs; the two sessions took 12.7 hours together. `src/` and `configs/` are the same at both commits |
| 2026-11-03 | Constrained answers are scored exactly like free ones: an answer that does not parse is a failure on an AST question and counts as correct on an irrelevance question | The same rules in both modes, so Update 10 compares like with like. 93 of the 34,750 constrained answers do not parse (81 cut off at 4,096 tokens, 12 stopped early), 40 of them on irrelevance questions |
| 2026-11-03 | The quantization penalty in each mode is the change from FP16 of the same model in the same mode. The constraint's effect on it is the difference of the two changes (constrained - free), with a bootstrap 95% interval that draws the same questions for all four runs | Each mode has its own baseline, so a constraint that helps FP16 and the quantized model equally does not count as removing a penalty. Drawing the same questions for all four runs keeps the pairing by question, as in Update 8. The 20 intervals are not corrected for multiple comparisons |
| 2026-11-03 | "Loss removed" (difference / size of the free loss) is given only for the 7 losses that were significant with free decoding. It may be above 100% or below 0% | A share of a change that may be zero is not meaningful; for the two smallest of the 7 (Qwen3-4B NF4, Qwen3-8B GPTQ) the interval of the difference includes 0, and the report says so. Values outside 0-100% are kept, because they are the finding (Llama-3.2-1B NF4 and GPTQ get worse) |
| 2026-11-03 | `src/gap.py` runs in the BFCL environment, because it reuses `src/taxonomy.py` for the transitions | No new package: numpy and jsonschema are already there |
| 2026-11-06 | The stress suite has 7 groups of 25 questions (175): six schema features from the plan (nested objects, enums, integer vs. float, optional arguments, unicode, 50-tool menus) and a plain control group without any of them. Each question has one correct call, every value is stated in the question, and each group has 3 or 4 levels | The control shows how well each model calls a function when nothing is stressed, so each feature can be measured against it, not against BFCL. Small single-call questions keep each failure tied to one feature; the levels show where a feature starts to break |
| 2026-11-06 | Enum questions give the meaning ("the Riga warehouse"), and the description maps each code to its meaning ("WH02 = Riga"), in a new random order for every question | The model must read the schema to pick the code, so world knowledge does not help, and any value outside the list (e.g. "Riga") is wrong. BFCL's checker ignores case, so "wh02" also counts |
| 2026-11-06 | Menu functions (5 actions x 10 objects = 50) have no argument descriptions; the correct function is placed in positions 1-10, 21-30 or 41-50 | With argument descriptions, 50 functions need about 4,150 tokens, more than the prompt budget of 4,096 (max_model_len 8,192 minus 4,096 answer tokens), which we keep the same as in the main runs. Measured with Qwen3's tokenizer and a copy of Llama-3.2's; the longest menu prompt is now 3,662 tokens |
| 2026-11-06 | The stress suite is scored with BFCL's checker, like the main questions: the menu group as BFCL's `multiple` category, the other groups as `simple`. Its functions have no BFCL language hint | One scorer for everything. Inside objects nested 2 or 3 levels deep, BFCL's checker compares strings exactly (elsewhere it ignores case, spaces and some punctuation), so those questions write the values exactly. The language hint ("in Python 3 syntax") belongs to BFCL's own questions |
| 2026-11-06 | Notebook 07 downloads the GPTQ and AWQ checkpoints from the private Hugging Face repositories at the commits used in Updates 6 and 9, and makes INT8 again | The same 4-bit weights as in the main results, with no quantization on Kaggle. INT8 takes under two minutes per model and was shown to give the same size in Update 9 |
| 2026-11-10 | Stress-suite results are read per group and level, in correct answers out of 25, next to the change in the plain control group of the same run. Each group is tested against FP16 of the same model and mode with McNemar's exact test, with Holm's correction over the 140 tests of each mode | The same tests as the main study. The control shows whether a change belongs to the feature or to the model as a whole. With 25 questions, a group must lose at least 13 (with no gains) to pass |
| 2026-11-10 | For a wrong value (M2), the analysis records whether the wrong argument is the one the group stresses (defined per group in `src/stress_analysis.py`) | Tells a failure of the feature from a failure elsewhere in the same call, such as the product ID in the number group |
| 2026-11-10 | For an answer that is not valid JSON (S1), the analysis checks whether it is right once only the closing brackets at its end are fixed. This is a diagnostic only: scores are not changed | Shows whether the content was right under a format error, while the scoring itself still repairs nothing |
| 2026-11-10 | The stress suite stays as it was run (v1), although the number group also has an ID argument that some models change | Changing questions after seeing the results would bias them; the problem is stated in the report and in the suite's README |
